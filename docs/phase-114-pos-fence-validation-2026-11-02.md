# Phase 114 cloud POS fence — local validation, 2026-11-02

Status: **INCOMPLETE / NOT READY TO DEPLOY.** A prepared database migration and disposable PostgreSQL test were added; the manager endpoint and cashier-facing recovery integration are not implemented. No production database or migration was touched.

## Mechanism

Phase 72 create_pos_sale inserts into pos_sale_requests before creating order, reservation or tender; Phase 100 wraps it and returns a receipt. The primary-key insert serializes transactions for a key, including ON CONFLICT retries. The new fence RPC attempts an insert using the same key, original cashier and request hash. If a sale committed first, it returns committed and its order ID; if its insert wins, it records the immutable manager/reason evidence in the same transaction. Existing create_pos_sale sees the already-present row without an order and rejects with pos_sale_still_processing. Identical retries remain rejected. Existing committed sale retries retain their original behavior. A pre-existing uncompleted request without cancellation evidence returns unresolved, never a fence. Hash or cashier mismatch is rejected. No historical rows are rewritten.

Only an existing admin or manager profile can invoke the operation, and only the service role is granted RPC access; the required web layer must independently authenticate that manager and enforce same-origin, without local-auth bypass. A 10–1000 character reason is required. Manager role alone does not prove original attempt identity: the web layer must preserve the exact cashier, key and hash and must not accept an unchecked handoff. A cancelled result must be persisted and displayed only after definitive server confirmation; a network timeout or not_found must remain unresolved. No user-facing replacement is enabled by this migration alone.

## Disposable local database tests

A new throwaway loopback PostgreSQL 18 cluster restored the retained schema-only Phase 2 snapshot and applied existing Phase 104 and prepared Phase 114 only to that disposable cluster. Six tests passed, zero failed: committed sale and same-key retry; fence first and repeated same-key sale rejection / repeated fence; cashier denial; an in-flight sale invisible to ordinary lookup while cancellation waits then returns committed; in-flight fence blocks concurrent sale; and immutable evidence. The test uses actual Phase 2 create_pos_sale_with_receipt and database processes, not mocked sale functions. The first run was discarded: pre-104 order-number truncation caused a duplicate synthetic order number. An initial sandbox attempt could not launch PostgreSQL due to restricted-token creation; the disposable run succeeded under local process permissions. Cluster was stopped; no production service was used.

Run from the Admin root with `node scripts/test-pos-sale-fence.mjs <path-to-pre-103-schema-only-snapshot>`. The test creates, mutates and destroys its own temporary cluster and schema; it never accepts a database URL. It requires native PostgreSQL 18 binaries at its configured test path. Do not point any test at production.

## Remaining blockers

- Implement and test an authenticated manager handoff and endpoint, including same-origin checks, exact request payload/hash verification, disabled/bypass accounts and denial during server outage. Existing attempt storage is keyed by cashier identity; signing a manager in changes that identity. Avoid a free-text identity handoff that can fence the wrong request.
- Integrate a compact action in existing recovery UI without releasing the active attempt on network failure or absent evidence. Preserve original key and recovery record, make cancellation repeatable, and distinguish an already committed receipt from a fenced request. Do not automatically create an offline sale.
- Add live database tests for missing database during cancellation, late requests after cancellation, post-sale receipt behavior, mismatched identity/reason, overlapping requests with explicit barrier synchronization, full permissions and Phase 2 regressions. The six above do not constitute full requested validation. Test setup uses timed scheduling for concurrency, so stronger synchronization is required before a safety claim.
- Validate migration against isolated Supabase staging and relevant Phase 3 migrations, check ownership, RLS, privileges, migrations and audit semantics, and review all privileged callers and deployment sequencing. Validate manager account authorization at both HTTP and database layers. Apply no production migration until separately approved.

No UI, RPC route, automatic transition, bridge, storefront, production environment or release was changed. This is an isolated preliminary migration and test, not a usable recovery feature or production GO.

## Follow-up: deterministic lock coordination

The disposable PostgreSQL 18 test now opens independent psql connections, waits for an explicit holder-ready marker and verifies via pg_stat_activity that the contender is blocked on a database lock before committing the holder. **10 tests passed, 0 failed**, including both sale/fence orderings, same-key retries, cashier denial, mismatched request hash, invalid reason, authenticated-role denial, unchanged committed order after a fence, and immutable fence evidence. This tests that the fence operation leaves the committed order unchanged; it does not prove general immutability of all Phase 2 sales.

The full Admin POS suite reported **41 passed, 1 failed**. The browser storage test timed out at Chrome CDP Page.enable; browser refresh and cross-tab behavior therefore remain unverified in this run.

The online sale request and pos_sale_requests record bind key, request hash and cashier, but contain no verified terminal or browser-session identity. Phase 114 has no terminal/session input. An authenticated manager endpoint cannot honestly reject cross-terminal or cross-session requests based on this existing contract. No endpoint or UI action was added that would bypass that requirement. A solution needs a trusted terminal/session binding captured before online submission, a database-backed identity association and a manager approval handoff that verifies the original request; historical unbound attempts need an explicit, separately reviewed policy.

The bridge cash input is strict and carries no original cloud key, fence evidence or resolution binding, and the signed journal envelope carries no such association. Supporting replacements safely needs a versioned bridge input and durable signed SQLite journal/outbox linkage, plus matching server ingestion validation and idempotency/reconciliation tests. Until that contract exists, replacement remains disabled and cancellation alone does not authorize a local sale. No cross-engine duplicate-prevention integration, database-unavailability endpoint, or manager UI was implemented or tested. No production deployment or migrations were performed.
