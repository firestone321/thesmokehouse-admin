# Phase 3 offline operational readiness — 2026-11-02

**Status: not ready for the intended complete offline Admin workflow.** The bridge implements a separate local cash POS; offline Orders and Dashboard are not implemented. The working trees were inspected; this does not establish what has been deployed or enabled. No production connection, migration, deployment, real payment or hardware command was made.

## Actual cashier workflows

The cloud Admin POS page renders the cloud sale workspace and, when POS_OFFLINE_ENABLED and the loopback bridge URL are configured, a separate collapsed Local cash station with an online provisioning form and a link that opens the bridge-hosted POS in a new tab (app/(admin)/pos/page.tsx:9, components/pos/offline-station.tsx:23). The local page is served independently by the bridge, not the Admin shell (smokehouse-pos-bridge/src/offline/ui.ts:1). It accepts only cash using a previously provisioned terminal, grant, PIN, signed catalog and allocation. The two interfaces have distinct carts, request identities and financial paths: this is **separate**, not unified.

- Online: staff can use the cloud sale workspace; offline preparation and the local POS link are separately available when enabled and configured. Nothing automatically chooses the local path.
- Internet fails before a sale: Admin navigation falls back to a generic offline page, while a previously provisioned local bridge page can cold-start on the registered computer if the bridge, authorization, PIN and allocation are valid. It must already be reachable by its local URL; Admin cannot be relied on to provide a link during a cold outage.
- Internet fails during cloud submission: the cloud request is preserved in IndexedDB, becomes outcome_unknown, and the UI offers original-outcome checking or retry of the original preserved request (lib/pos/use-pos-sale.ts:70, components/pos/pos-sale-workspace.tsx:169). No automatic fallback creates a local sale. The separate local POS cannot see the cloud attempt: if staff switch and re-enter the same physical sale before resolving it, independent identifiers do not prevent a duplicate financial sale.
- Bridge unavailable: the local page and its local journal are unavailable; local cash commitment and local hardware cannot work until the service returns. Cloud posting can remain available independently; check hardware status rather than assuming drawer or print occurred.
- Connectivity returns: the bridge synchronization worker retries original signed envelopes if OFFLINE_SYNC_ENABLED=true and the service and endpoint are healthy (bridge src/offline/runtime.ts:53, src/offline/sync-worker.ts:27). It is not dependent on a browser being open. It does not automatically switch the cashier back to cloud POS.
- During synchronization: the local interface shows its pending count and recent local sales with individual synchronization/hardware states; a collapsed manually refreshed status panel exposes more diagnostics (bridge src/offline/ui.ts:7, 36, 54). This is not integrated into Admin Orders or Dashboard. Do not infer cloud confirmation from the local commitment message.

## Functional evidence and gaps

The SQLite journal atomically records a signed cash sale, outbox entry, sequence, allocated-stock deduction and hardware action identities (bridge src/offline/journal.ts:172–216). Same-ID duplicate handling cannot identify an independently re-entered sale. Drawer and receipt are separate durable operations; original dispatch attempts drawer before receipt and reprints are receipt-only (bridge src/offline/hardware.ts:9, router.ts:75). Ambiguous hardware outcomes are not automatically replayed. Physical output is not guaranteed by a software acknowledgement.

Synchronization preserves immutable original envelopes, retries ambiguous delivery, records acknowledgements and quarantines conflicts (bridge src/offline/sync-worker.ts:39; journal.ts:272). It is configurable and not established enabled in production. Terminal revocation cannot reach a disconnected terminal instantly; it depends on previously issued grant expiry and delivery of control information. Review the exposure window during staging and field validation.

Orders loads live cloud data (app/(admin)/orders/page.tsx:26); Dashboard fetches server snapshots and revenue analytics (app/(admin)/dashboard/page.tsx:7). The service worker returns the generic offline page for failed navigations (public/sw.js:40). No implementation was found for a read-only cache of cloud orders, a combined cloud/local order list, or a cached operational Dashboard with last sync, pending sales and separately labeled confirmed totals. Previously loaded browser screens may remain visible but are not a verified offline feature.

Phase 113 derives the default initial minimum by ceiling 65% of eligible physical resources and funds stock under locks; replenishment is bounded and requires confirmation and activation (db/phase-113-dynamic-pos-allocation.sql:77,147,225). It does not modify menu prices. Offline ingestion inserts original item price snapshots into orders and items rather than updating menu prices (db/phase-106-offline-cash-ingestion.sql:170). These are code observations and local unit-test evidence, not a new full-schema integration or storefront end-to-end result.

## Smallest safe integration

Present the existing cloud and local workflows within a single cashier-facing shell with an explicit selected mode and a clear offline/bridge state. Keep cloud and local financial submissions separate. Persist and check unresolved cloud attempt identity before allowing a transition to local recording for the same sale; never use a timeout alone as permission to create a replacement. Preserve original request recovery, require deliberate resolution of unknown outcomes, and retain independent bridge authorization, allocation and action identities. A cold-start local shell needs an independently reachable local entry point and an approved secure connection model; the current bridge page sets frame-ancestors none. Offline Orders/Dashboard require purpose-built scoped read-only caches, timestamps, access controls and clear unconfirmed labels. This is substantial integration and was not implemented without review.
